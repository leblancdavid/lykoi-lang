### Scope: local capability is not cumulative achievement

The frozen Phase 5C benchmark is cumulative. R5.101 is a current **capability
diagnostic**, not a resumed frozen maintenance competition. Each case's local
obligations are evaluated against the unchanged `air/task_manager.json`, with
the baseline and frozen requirement conventions recorded in the FRC context.
Precursor dependencies are retained as demands and are analyzed below; they are
never manufactured as fixtures/adapters to obtain a whole-case pass.

Thus **1/20 is a requirement-local pipeline success**, not twenty-request
cumulative coverage or a new achieved history. B05's domain is the source's
`pending|completed`; behavior outside that domain has no new specified error
authority and is not scored. The supported query returns the current model's
whole task records. It does **not** demonstrate B02 tags, B04 source fields, or
other earlier changes on a cumulative B05 store. **No new full cumulative
benchmark success is established by R5.101.** The historical achieved Lykoi set
remains `{B01,B04}` in its own preserved workspace/history.

This split matters: counting only cumulative prerequisite failures would hide
the newly executable equality query; silently supplying all missing precursor
fields would overstate current coverage.

## Formalization and obligation review

Every frozen B01–B20 file was inspected, together with
`benchmark/requirements/README.md` and `benchmark/baseline.md`. Every case has
an eight-part inventory in the published evidence: **operations, input,
selection/transformation, ordering, validation, state effects, result behavior,
persistence**. Identity, relationships, clocks, invariants, atomicity and
permissions are represented in the relevant parts rather than omitted.

Common authority retained: normal `(created_at,id)` ascending list order;
explicit atomic/idempotent migration on field additions; old reads refuse with
`migration_required`; JSON success/error behavior and exit status; existing
command compatibility; failed changes preserve observable state. Per-case
explicit changes override earlier behavior, particularly archival, deletion,
ownership and authorization. Migration retry after user creation is not lost.

The normal producer interface receives recorded interpretations by the available
agent. These are **evaluation data**, not a prose parser, benchmark lookup in
the compiler, or an added structural adapter. Pure queries B03/B05 receive all
nine current typed facets. B06/B10 retain those query facets **and** their
unsupported mutation/migration obligations. Other demands remain explicit FRC
relations supported by the existing envelope, without pretending opaque JSON
parameters have executable semantic meaning. A necessary unmapped clause is
enough for structural refusal even if another clause, such as a legacy default
or constant HIGH selection, has an existing partial mapping.

Current formalization is an inspectable **candidate inventory**: source-bound
FRC validation and exact SOI reconciliation pass for eighteen candidates.
The records use same-agent source inventories and broad source spans; analytical
review and synthetic test-owner credentials do **not** establish independent

### Ambiguity still matters after exposure

- **B17:** existing non-system B16 users must acquire a role under the common
  explicit-migration rule. B17 supplies `USER` for *new user creation* and `ADMIN`
  for system, but no role default for those old users. Treating a creation default
  as migration authority would repeat a known default-trigger error. Native
  reconciliation is `DISPUTED` with a blocking question; normalized result is
  `FORMALIZATION / NEEDS_CLARIFICATION`.
- **B20:** adding an existing project member requires an existing user, but the
  error for a nonexistent member user is not specified. The common missing-ID
  convention says `task_not_found` for tasks; it does not settle user lookup.
  `invalid_owner` covers the project owner, and `project_not_found` covers a
  project, not its member. The same native clarification halt is retained.

These are material, observable authority gaps under the common error/migration
contract. They are not claims that every clause of B17/B20 is ambiguous. Both
requirements also demand clear but currently missing capabilities. No answers
were invented. Other details (e.g. exact starting audit sequence number or ID
format beyond uniqueness) remain implementation freedom where no exact value
is required; they are not promoted to blockers. Historical public B01 default
questions remain historical results: this frozen B01 explicitly says missing
priority remains NORMAL, and its current first blocker is structural.

### Why the six integration-first cases are not six new language primitives

- **B01/B04:** legacy enum extension, exact literal filtering, `input_default`,
  verbatim scalar assignment, literal migration and persistence already have
  executable meaning. The closed normal bridge and faithful legacy mappings
  do not carry the complete requested evolution. Historical successful model
  authoring is preserved; a stricter normal front end now refusing those requests
  does not mean the backend lost their semantics.
- **B13:** equality rejection guards, lifecycle transitions and repeated-transition
  errors already exist. Cross-operation invariant mapping is missing. Its
  archive/notes prerequisites remain unsatisfied; this is not a whole-case
  semantics-complete claim.
- **B03:** string-list membership, comparison, blank rejection, ordering,
  inclusion, results and read-only effects all validate as typed query facets.
  `query_profile.structural` checks storage binding *at the structural layer*;
  it records `UNSUPPORTED_COLLECTION_STORE`, reason `Unsupported nullable/missing
  query field`, because canonical tasks have no tags. Thus its normalized first
  stage is STRUCTURAL, although the **root immediate gap is application/store
  integration**. Persisted mutable string arrays are a deeper missing prerequisite.
  No JSON-array substitute or invented tags field was used to call B03 successful.
- **B08:** boolean query types and equality inclusion already exist in the query
  profile. The legacy task field/store path accepts only strings/timestamps/enums,
  so it cannot persist the required boolean or expose it through the model adapter.
  Integrate the existing typed concept; do not invent a benchmark-specific archive
  type. Cross-list composition and guarded mutation are additional demands.
- **B18:** generic `effects` relations map to `external_effect` channels and pass
  native structural coverage; BDI then refuses `unsupported_observation` with
  missing `rule_for:external_effect`. This is a discovery/structural-interface
  integration gap. The native shallow projection does not prove comprehensive
  event understanding. Durable ordered event and transaction semantics are also
  genuinely missing downstream; an added discovery rule alone would not implement
  auditing. Adequacy, V1 and compilation are **NOT_REACHED**.

## Recommended next four general development rounds (proposals only)

1. **Normal-path closure for existing model evolution and scalar/lifecycle
   semantics.** Carry typed defaults, verbatim field additions, enum evolution,
   simple guards and migration preservation through structural review, BDI,
   adequacy, faithful V1 and authoring. Include mixed query/legacy obligations
   and explicit field/store binding. Demonstrate synthetic non-task models;
   accepting opaque descriptions or skipping later gates is not completion.
2. **Composable typed values and mutation transformations.** Unify field/store
   types with existing query booleans/string lists, and add minimal general
   presence-aware trim/validate/map, ordered value append and stable dedup/set
   operations. Separate comparison normalization from stored transformations.
   Start with bounded scalar and ordered-string operations; integer/null support
   is another explicit milestone, not implicit support from Python values.
3. **Typed predicate composition and guarded operations.** Build on those
   values: null-aware tests, scalar-in-set/AND/OR/NOT, runtime temporal ranges,
   cross-input validation, clock references and guard reuse across commands.
   Keep calendar arithmetic separately specified. Relationship quantification
   requires the next round's relation model; do not claim it early.
4. **Persistent identity relationships and composable atomic effects.** Stage
   this project: same-state references/quantified guards and graph integrity;
   then multi-entity state and referential migration; then explicit transactional
   event/conditional-create composition with clock/ID resources. Each milestone
   needs its own structural/BDI/V1/backend/external behavior evidence. It is not
   one special audit/recurrence/project primitive.

**Highest useful next leverage:** A first, then B. A stops the front end from
refusing already available software abstractions; B's nine direct demands and
five archival-dependent demands make it the largest reusable semantic/type
cluster. C/E/F remain necessary; neither A nor B alone yields broad twenty-case
coverage. Temporal arithmetic and event transactions are smaller in direct
count but important for eventual coverage and general software usefulness.

Do not build `ListTag`, `ArchiveTask`, `CriticalPriority`, `DailyRecurringTask`,
`ProjectPermission`, or a twenty-case FRC/prose lookup as privileged semantic
primitives. Avoid per-case generated Python patches, invented prerequisite
models, dummy query parameters, query/store aliases that bypass persisted
shape, oracle-derived output templates, or a controller governance expansion
unrelated to behavior. Aggregation/pagination/regex search are not evidenced
local demands here and should not be prioritized from this corpus alone.
