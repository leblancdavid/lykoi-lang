# R6.31 — H2 genuine in-place modification protocol 1

**Prospective only.** Question: can AI change interconnected existing symbolic
software with fewer defects/regressions or lower effort than equivalent Python
and fixed intent? No abstraction discovery occurs here.

## 1. Application eligibility and existing shortlist

An eligible application already has accepted A/B/C equivalents before modification
selection: at least4 interacting operations,2 callers/consumers of a shared rule,
persistent shared state,2 behavioral invariants, conditional guarded transitions,
restart/rejection behavior and regression-sensitive sequences. Record exact base
source/intent/model/generated identities, public contracts and baseline observations.
Equivalence means the same external behavior, not source similarity.

The existing R6.16 kiln firing-permit and evidence custody-seal implementations are
an **exposed shortlist** with real persistence/guards/invariants. Preserve originals,
use successor copies only. Strictly accepted B/C bases exist; original A has a
blank-label error, so it is not an equivalent accepted H2 starting point. A corrected
copy would require separately authorized unscored fixture preparation, named and
costed explicitly; it cannot replace the historical A result. Verify caller counts
and eligibility before selecting either. These two domains share one skeleton.

Main study: **4 applications, at least2 nonisomorphic behavioral skeletons**.
An independent selector uses a preordered existing candidate pool, public semantic
scope and eligibility above, without seeing proposed changes or expected winners.
Additional existing fixtures need qualification, not new language meanings.
If fewer than4 eligible equivalents are available, report a prerequisite gap for
that successor; a two-application one-family pilot remains exploratory and cannot
be silently substituted for this main design.

## 2. Withheld change classes

Four independently frozen branches/application, each resetting to its accepted
base (no cumulative order advantage):

| Class | Required genuine edit | Discriminating expectations |
| --- | --- | --- |
| M1 shared invariant | Change one existing invariant consulted on load/commit and by at least2 operations | Newly valid/invalid states, both consumers, rejected-byte preservation, valid restart |
| M2 shared transition | Alter an existing transition/guard used by2 callers, retaining state identity | Both callers change on same witness state; untouched transition remains correct |
| M3 validation exception | Introduce a category/condition exception into an existing rule while preserving its ordinary branch | Positive exception, nearby negative condition, ordinary rejection, existing operation and invariant consistency |
| M4 ordering/refactor | Change precedence of2 existing competing validations across consumers; for half the applications instead perform a shared-logic extraction with no external change | Conflict cases detect old precedence; refactor has unchanged external suite and verified shared-use structural obligation |

Exact rules, changed obligations, witness states, supersessions and error precedence
are commissioned later and frozen **before any modifier session**. Examples above
are selection classes, not participant task solutions. Require at least2 distinguishing
inputs/sequences per changed consumer, plus unaffected callers, and no new endpoint
can satisfy a changed-operation requirement. Refactor-only cases have no intentional
external delta and are separately labeled, not pooled as changed-observation successes.

## 3. Editable successor and caller integrity

Each track receives its own accepted base and identical released functional change.
New session/context for each application/change/replicate/track. Author must read
the supplied existing artifact, record a predicted semantic/consumer impact set
before editing, then supply a patch or revision with exact base identity precondition.
Record full replacement versus targeted edit and bytes/semantic objects changed;
full-file submission is allowed but cannot masquerade as a small patch.

C facade only loads/copies existing IR and invokes frozen validators/lowerers; no
new runtime operation, task logic or automatic semantic repair. A symbol/body change
creates a successor identity. Every intended caller explicitly updates its pin;
unintended callers retain old pins where required. Check stale references/missing
closure on publication. One atomic deployment manifest switches the **existing**
operation set/state path to the candidate revision. Running old endpoints alongside
new alternatives fails changed-behavior witnesses. Preservation refers to original
research artifacts, not mechanical retention of old deployed behavior.

B receives equivalent snapshot/diff/selftest facilities. C's legacy impact coverage
gaps remain visible; absence of automatic tooling is not filled by an oracle-derived
impact hint. Python and intent callers can be traced through ordinary code/graphs.

## 4. Separate baseline and modification evaluation

Evaluate and seal all accepted base equivalents **before reveal**. No base authoring
score is pooled with modifier effort. Fixture preparation and correction cost is
recorded separately and in full workflow totals. Invalid baseline means modification
not reached, not a regression-free success.

**4 applications ×4 branches ×3 tracks ×3 replicates =144 modification sessions.**
Use the same600s/40 model calls/64 tool calls/64,000 input+output tokens/4,096 output
per response, first plus2 resubmissions,4×16 selftests and tool/scorer caps as H1.
Counterbalance tracks/change order; no hidden acceptance feedback during repairs.
Freeze first and final modified artifacts and every failed candidate.

For each base snapshot separately report its original expected behavior. For each
modified candidate report new/superseded obligations, retained original observations,
unintended changes, state/restart effects and strict full-checkpoint acceptance.
An authorized changed expectation is not a passing-to-failing regression. Refactor
cases retain all original expectations. Include mixed operation sequences to expose
changes visible through another consumer rather than the edited method alone.

[Impact and regression scoring](ACCEPTANCE-AND-SCORING.md) uses a separate frozen
obligation/caller oracle. No C-specific benefit is credited for a check equivalently
supplied by B. H2 may support fixed symbolic modification even if H1 fails; H1
transfer cannot rescue H2 regressions or missing stateful capability.
