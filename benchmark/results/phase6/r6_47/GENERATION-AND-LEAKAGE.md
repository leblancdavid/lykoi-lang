# Prospective data generation, deduplication and separation

This is a plan. No new requirements or solutions were generated in R6.47.

## Generation process

1. Freeze a target profile/version and explicit excluded semantics. Separate the
   stateless wrapper study from broader26-construct production work; never quietly
   mix incompatible vocabularies or add operations to satisfy generated tasks.
2. Appoint a task generator/curator independent of candidate builders and evaluation
   solutions. Source varied requirements without compiler-gap/outcome tailoring;
   preserve author/source permissions, raw wording and clarification history.
   A fresh same-platform session alone does not attest independence. Disclose weaker
   access boundaries if stronger separation cannot be established.
3. Before authoring, clarify requirements and freeze candidate-output-independent
   functional expectations. Obtain separate source-authoritative review, especially
   errors, persistence format, authority, coordinates and successor behavior.
4. Collect actual direct and tool-assisted construction under fixed budgets, recording
   visible calls/arguments/feedback and errors. No curator repairs disappear from
   provenance. Preserve the first candidate and every subsequent actual correction.
5. Deterministically validate exact targets using existing frozen tooling; separately
   test functional behavior with AI-free external execution. Acceptance includes
   positive, invalid and conflicting-error cases and relevant invariant/persistence
   obligations. Validate-once/public-execute differences remain labeled.
6. Replay accepted and failed artifacts without model calls; bind complete envelopes,
   bytes, state, dependency pins and declared provenance projection. Replay agreement
   alone is not acceptance. Preserve partial results and infrastructure stops.
7. Join source→contract→target→validation→acceptance→replay by immutable identities;
   assign technical and provenance labels; quarantine ambiguity, missing turns and
   incorrect final targets. Do not delete failures to make the dataset look easier.
8. Deduplicate and group **before** train/development/evaluation allocation. Publish
   admission and exclusion manifests, tokenizer-length distributions and failure rates.
   Only then consider separately authorized training.

## Multi-level deduplication

- Byte SHA256 and strict canonical JSON find identical/reformatted targets.
- Normalize bound names and symbol/caller labels for a structural similarity index;
  recursively resolve dependency bodies for that index. Retain raw original identities.
- Compare typed DAG shape, ordered checks/errors, literal/parameter roles, input/output
  layouts, state schema, effect boundaries and successor relation. Do not normalize
  away meaningful check order, state topology, coordinates or required literal values.
- Flag constant-only variants, renamed enums and shared generators as one template
  cluster. Use requirement-family review to avoid calling each bias a new behavior.
- Cross-link compact/expanded/flat/generated forms. Raw envelopes may differ; their
  shared ancestry still creates leakage even without exact behavioral equivalence.
- Include transitive reusable-definition ancestry and entire application skeletons.
  Fingerprints are leakage detectors, not a universal semantic equivalence solver.

## Split as connected components, never random example rows

Create a graph over records. Edges connect exact/alpha/template duplicates, common
application skeleton, generator lineage, predecessor/successor, both callers,
modification stages, and reusable abstraction definition/closure. All connected
records belong to one split. A and B views, negative attempts, feedback, replay,
summaries and generated code follow the same component.

| Leakage | Required control |
|---|---|
| Exact solution | Cross-split byte and canonical fingerprints must have0 overlap |
| Renamed variables | Alpha-bound graph matching plus requirement review |
| Template family | Constant/enum/formula generators grouped; variants not randomly split |
| Shared application skeleton | Whole kiln/custody-like scaffolds grouped even if names differ |
| Modification successor | Entire baseline/change/retained-caller trajectory assigned together |
| Abstraction definition | Definitions and all dependent tasks co-located; or a separately labeled reuse-transfer tier |

A **reuse-transfer evaluation** may intentionally share a public primitive vocabulary
or explicitly supplied frozen library, but it is not an abstraction-unseen tier.
A stronger family-unseen tier holds out requirement/scaffold and discovered-definition
ancestry; only the common language specification and fixed primitive meanings may be
shared. Both tiers keep evaluation solutions/oracles out of training and retrieval.

Evaluation families are commissioned and sealed before dataset builders see their
contents; a custodian checks fingerprints without releasing solutions. Future
benchmark solutions never become training examples. Revealed families retire from
unseen evaluation permanently. All R6.36–R6.46 tasks and B01–B20 are already exposed;
none can certify new held-out generalization.

## Smallest justified data-only pilot

Recommend **12 complete episodes**, six genuinely different requirement/scaffold
families ×two behavioral contracts: four development/training families (8 episodes)
and two custodian-held evaluation families (4 episodes). Allocate families before
authoring; do not publish hidden evaluation solutions into a training repository.
Count base/successor and A/B views inside their episode. This size is a process pilot,
not a universal SFT minimum or statistically adequate effectiveness study.

Why12: two contracts per family expose renamed/constant/template leakage; four
development families challenge coverage beyond the current single domain; two
unseen families avoid a single lucky transfer case. Acceptance should include one
natural diagnostic correction when it occurs, without fabricating model errors.
If the frozen subset cannot express diverse families, record that limit rather than
add new primitives. A broader production pilot needs its own faithful tool facade;
existing arithmetic lifecycle MCP tools cannot author stateful26-construct programs.

Pilot gate:100% source/target/evidence joins;100% admitted targets pass deterministic
and frozen functional checks and AI-free replay;0 split-component overlaps; independent
review disclosure; all failed attempts retained. Failure at a gate stops expansion.
No training is necessary to find out whether this data pipeline is trustworthy.
