# R6.37 — Unseen symbolic lifecycle and token attribution

**Final classification: `R6_37_LIFECYCLE_SUPPORTED_ATTRIBUTION_PARTIAL`.**

GPT-6.1 Sol completed one fresh-to-participant, bounded symbolic lifecycle using
**actual semantic MCP calls**. Original acceptance passed **448/448** observations;
final acceptance passed **633/633**. Three AI-independent replay passes each passed
**633/633**, reproducing complete result envelopes, logical work, pinned identities,
expanded plans and provenance maps. Five definitions were admitted on their first
proposals, with no scored rejection, correction or coordinator semantic repair.

Actual per-completion usage is retained. Exact provider request serialization and
complete fixed context are unavailable, so token-category attribution is **partial**.
Visible local estimates identify tool feedback and accumulated history as substantial
volumes, but establish no dominant provider-token cause. This result does not establish
superiority over Python or structured intent, unbiased unseen generalization, or
proportional token scaling with lifecycle complexity.

## Frozen fresh requirement and independent expectations

[Original requirement](r6_37/REQUIREMENT.txt), [staged modification](r6_37/MODIFICATION.txt),
[semantic guide](r6_37/GUIDE.txt), [selection provenance](r6_37/TASK-PROVENANCE.json),
[acceptance expectations](r6_37/ACCEPTANCE-EXPECTATIONS.json),
[oracle source](../../../experiments/ai_lifecycle_r6_37/lifecycle_run.py) and
[model/budget](r6_37/MODEL.json) were bound in [TASK-FREEZE](r6_37/TASK-FREEZE.json)
before participant authoring.

`WindowCharge(start:Int64,end:Int64,cap:Int64)->Int64` checks, in order:
start nonnegative, end within cap, and twice start no greater than end. It returns
end+start. CallerA reads two bytes, checks end-of-input before composition, uses
cap200 and adds3. CallerB reads one byte, checks end-of-input before computation,
derives end=start+20 and uses cap180. The behavioral successor returns end+start+start
while retaining the signature/checks. Only CallerA is explicitly migrated; CallerB
retains its predecessor pin.

The task is coordinator-designed and capability-tailored, distinct from the inspected
Increment, OffsetTotal and BoundedScore examples. It is fresh to the recorded participant
session; exhaustive historical uniqueness and external independent sourcing are not
established. The supplied source labels permit exact error-node assertions but do not
constitute a completed symbolic solution.

Expectations derive from the requirement and frozen semantic definitions, before
participant output. They cover typed integer values and UInt16BE bytes; all three
semantic error codes/stages/offsets/hygienic source nodes; truncated/trailing data;
static Bool-as-Int64 rejection; encode range; ordered failure precedence; positive
work and VM work-limit classifications; exact dependency identities; and root spans.
Original coverage includes169 selected A byte pairs, all256 B byte inputs and23
invalid/probe/limit observations. Final coverage adds185 successor observations.
These are observation counts, not claims that every row is a distinct input.

This is AI-independent expectation construction, not independent human/cognitive
review: the same coordinator selected the requirement and implemented the oracle.
Exact work is implementation-dependent rather than prescribed by the requirement;
its full value is compared on replay. The VM provides no execution trace: ordering
is evidenced by conflicting-error cases and unchanged expanded ordered plans.

### Growth and competing explanations

Observed processed input grows from975 at the first scored completion to21,029 at
the last. Modification input costs109,306 across eight completions versus26,263
across seven original completions. Both stages operate in one accumulating session;
retrieved definitions, dependency records, validation maps and execution feedback
are repeatedly present. Local estimated F is the largest visible repeated category,
followed by E. These are **content-volume estimates**, not defensible exact
provider-token dominance percentages.

- **E1 instruction overhead:** not established. A/B/C estimate14,205 repeated input
  tokens, but actual fixed context and schema serialization remain unknown.
- **E2 construction overhead:** consistent with observed history growth and the
  larger visible feedback/history volume. No correction was needed; this is mainly
  successful tool feedback/retrieval and ordinary history, not a repair loop.
  Semantic decision-making itself is not isolated by the measurements.
- **Dominant provider-token cause:** inconclusive; exact category attribution is absent.
- **Caching:**101,888 read-cache tokens demonstrate reported reuse, approximately75%
  of scored processed input. Effective monetary savings and category-specific cache
  allocation are unknown; cached processing is still processing volume.
- **Complexity proportionality:** not determined from one task/two sequential stages.
  Complexity, history length, tool output size and caching are confounded.

No claim is made that removing guidance would preserve correctness. No token count
or SDK cost0 is treated as an API billing receipt. Coordinator/preparation/publication
model usage and a fully costed development workflow remain unknown.
